# Pipeline no GitHub Actions: CI, segurança e deploy na Vercel (plano)

Data: 2026-10-22. Ticket da pipeline no Linear. Pedido do dono: "vamos implementar uma pipeline no github actions para o deploy" e "inclua na pipeline execução de testes, scans de segurança, linters e outras coisas que julguemos relevantes". Escopo aprovado na conversa (preview por PR, Lighthouse e Playwright ficam para depois).

## Decisões

- **Um caminho para produção.** A Vercel não é conectada ao GitHub; só o workflow de deploy publica. Migração do banco antes do deploy, no mesmo job.
- **Checks obrigatórios em `main`:** `ci` e `codeql`. Proteção da branch ativada depois do merge deste plano (PR obrigatório, checks verdes, sem push direto).
- **Segredos** só no environment `production` do GitHub: `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, `DATABASE_URL`. Cadastrados pelo dono. O job de deploy é pulado (não falha) enquanto `VERCEL_PROJECT_ID` não existir, para o workflow poder ser mergeado antes das contas.
- **Segurança dos próprios workflows:** `permissions` mínimas por job (`contents: read` como padrão), actions fixadas por SHA com comentário da versão, `concurrency` por ref cancelando execuções antigas, sem `pull_request_target`, sem interpolação de entrada não confiável em `run`.
- **Lint:** ESLint 9 flat config com `eslint-config-next` (core-web-vitals + typescript). Violações existentes no código são corrigidas no mesmo PR quando pequenas; regras só são desligadas com justificativa em comentário.

## Arquivos

- `.github/workflows/ci.yml` — `pull_request` e `push` em `main`. Jobs: `verificar` (Node 22 do `engines`, `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`), `auditoria` (`npm audit --omit=dev --audit-level=high`: só dependências de produção, porque o `eslint-config-next` traz alertas altos sem correção publicada que existem só nas dependências de desenvolvimento), `workflows` (actionlint + zizmor), `segredos` (gitleaks sobre o diff). Nome do job agregador `ci` que depende dos quatro (`needs`) para ser o único check obrigatório.
- `.github/workflows/codeql.yml` — CodeQL JS/TS em `pull_request`, `push` em `main` e semanal; `permissions: security-events: write`.
- `.github/workflows/deploy.yml` — `push` em `main` e `workflow_dispatch`; `concurrency: producao` sem cancelar; job `deploy` com `environment: production`: checa se `VERCEL_PROJECT_ID` existe (senão termina com aviso), `npm ci`, `npx vercel pull --yes --environment=production`, `npx vercel build --prod`, `npx drizzle-kit migrate` com `DATABASE_URL`, `npx vercel deploy --prebuilt --prod`, e imprime a URL no resumo do job. Roda só depois do `ci` verde no mesmo commit (`workflow_run` de `ci` concluído com sucesso em `main`, ou `needs` dentro do mesmo arquivo; escolher `needs` chamando os mesmos jobs via `workflow_call` se simplificar).
- `.github/workflows/fontes.yml` — semanal (segunda 09:00 America/Sao_Paulo ≈ 12:00 UTC) e `workflow_dispatch`: `npx tsx scripts/verificar-fontes.ts`; em falha, abre ou atualiza uma issue "Link de checagem quebrado" com a saída (`permissions: issues: write`).
- `.github/dependabot.yml` — npm e github-actions, semanal, agrupando atualizações menores.
- `eslint.config.mjs`, `package.json` (`"lint": "eslint ."`, devDependencies `eslint`, `eslint-config-next`), ajustes de lint no código se houver.
- `README.md` — seção "Pipeline" curta: o que roda em cada PR, como o deploy acontece, quais segredos existem e onde.

## Verificação

- Local: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; `actionlint` e `uvx zizmor .github/workflows` sem achados.
- No PR: os quatro jobs de `ci` e o `codeql` verdes. O `deploy` não roda em PR: só dispara em push para `main` ou manualmente a partir de `main`, e lá é pulado com um aviso (sem falha) enquanto os segredos não existirem.
- Depois do merge: proteção de `main` com `ci` e `codeql` obrigatórios; primeiro deploy real com os segredos cadastrados (ticket de deploy).
